The project in one minute

Calcio Champagne is a reproducible football data system that asks whether incoming transfer spending accompanies an improvement in next season’s recorded attacking output, and whether attacking output tracks same-season league finish. It combines pinned CSV acquisition, PostgreSQL, a Python processing pipeline, measured infrastructure and a browser application. The primary model improves modestly over a zero-change baseline. A separate comparison reports score-derived GF/GA/GD and league ranks, observed shots, shots on target and corners, plus descriptive Poisson attack/defense ranks. The source has no provider xG; an SOT-based conversion proxy is explicitly experimental. A goalkeeper cross-check and red-card association are presented with their coverage and limits. The primary Transfermarkt-derived dataset’s licence remains unconfirmed.

Reading the comparison numbers. GF is goals scored, GA is goals conceded, GD is GF minus GA. The attack rank orders goals scored per match from highest to lowest, the defense rank orders goals conceded per match from lowest to highest, both within one league and season, and tied rates share a rank. xG is not in the loaded data and cannot be derived from a scoreline.

Data and the database

Scope: Sources → validation → bulk load → schema and SQL

What you need to know

  • Which exact copy of the data we use. loader/sources.json pins one revision of the upstream repository — a revision is a specific saved version, like a dated edition of a report — and stores a SHA-256 checksum for every file. A checksum is a fingerprint of the file's contents: change one character and the fingerprint changes. That is how we prove we loaded the data we documented.
  • One row of our analysis is one club, in one season, in one competition. The club's name is only a label. Two spellings of the same club must never become two clubs, so every join uses the numeric club ID, not the name.
  • Why a relational (SQL) database: our eleven files have fixed columns, and we constantly combine players with clubs, seasons and competitions. That combining is called a join, and relational databases are built for it. A document database would store the same facts but make these joins harder, not easier.
  • What COPY does: it is PostgreSQL's bulk-loading command. It streams a whole file into a table instead of sending one INSERT statement per row, which is why 5,743,186 rows load in about ten seconds.
  • Why we build indices after loading, not before. An index works like the index at the back of a book: it makes lookups fast, but it must be updated for every row inserted. Building it once after the import is faster than maintaining it during the import. ANALYZE then refreshes the statistics the database uses to pick a query plan.
  • The match files from football-data.co.uk are optional. Without them the system still runs and the interface states that coverage is missing instead of showing zeros. Club names in those files are mapped to our IDs, identical fixtures load once, and contradictory scores stop the replacement before stored matches change.
  • The licence of the primary source is not confirmed. We checked: there is no licence file at the pinned revision. Being publicly downloadable is not permission to reuse. Say this plainly — it is a known open item, not a mistake to hide.
  • One legacy table (team_competitions_seasons) differs from the current upstream file: 196,378 rows with seven fields locally, 58,247 rows with 29 fields upstream. We kept the local file instead of silently replacing it, and the Champagne Index and the model do not use it.

What to show

  1. Open loader/sources.json on screen and read one entry aloud: the revision, the file name, its checksum and the expected column order.
  2. Open sql/champagne_queries.sql and point at the GROUP BY: club ID, season, competition. Explain that MAX(team_name) only picks a label to display.
  3. Open tests/test_match_loader.py and show one rejected case: a fixture whose stated result disagrees with its score never becomes a stored match.

Your spoken part

Our data layer uses eleven pinned CSV tables. We chose PostgreSQL because the records have fixed schemas and are joined by player, club, competition and season. The loader validates headers, uses COPY for bulk import, and builds indices afterwards. We aggregate by canonical identifiers so name aliases do not duplicate observations. An optional match source adds actual scorelines and standings. Invalid or duplicate matches are handled explicitly. The source is publicly downloadable, but its licence is still unconfirmed; we do not claim that this requirement is resolved.

Hand over: “With the data stored consistently, the next step is to define a valid season-to-season target and evaluate it.”

Analysis and the model

Scope: Index → features → target → baseline → limits

What you need to know

  • The Champagne Index formula: recorded goals plus assists, divided by the matches the source reports for that club-season. Because goals and assists are counted separately, one goal with an assist contributes twice. It is our own proxy for attacking output, not xG and not an official rating.
  • The target is the next consecutive season's index minus the current one. A season pair only counts with at least 30 matches in both seasons for the top five leagues, and five for other competitions.
  • The five features: the current index, total incoming spend, spend on attacking players, average squad age, and the change in average market value.
  • How the wrong lag was removed: build one row per club and season first, attach the exact previous year, and only then join competitions. Done in the other order, a club playing three competitions is counted three times before the lag is computed.
  • The chronological holdout: earlier seasons train the model, later seasons test it, and the baseline predicts no change at all on those same test rows. A random split would let future seasons leak into training.
  • R² = 0.127 does not mean 12.7% accuracy, and it is not a share of correct predictions. The honest comparison is MAE 0.4856 against the baseline's 0.5114 — about five percent better.
  • The Lab uses a separate model fitted on all eligible data for exploration. Its own fit is not an independent test, and moving a budget slider shows a learned association, not the effect of an actual transfer.
  • The season comparison also shows goals for, goals against, goal difference and per-match attack and defense ranks derived from real scorelines. Those are separate from the Transfermarkt-based index.
  • The defensive-spend follow-up correlates defender fees with the next-season change in goals conceded per match: r = 0.0040, p = 0.427, n = 38,531. There is no useful linear signal.

What to show

  1. Open the Project page and read the current r, p, n and MAE aloud, naming the units and the sample behind each one.
  2. Explain why a 23/24 → 25/26 pair is invalid even though a naive shift by one row returns it.
  3. Change one input in the Lab, return to the baseline, and say what the comparison between the two actually measures.

Your spoken part

We define attacking output as recorded goals plus assists per source match. The target is the change in that index in the next consecutive season. We remove incomplete season pairs and construct lagged squad values before joining competitions. Evaluation uses earlier seasons for training and later seasons for testing. The RandomForest has a test MAE of about 0.486, compared with 0.511 for predicting no change: an improvement of roughly five percent. This is a modest signal. The comparison also separates the Transfermarkt attacking index from completed league scores: goals for, goals against, their difference, and per-match attack and defense ranks. A defensive-spend follow-up also has almost zero association with next-season conceded-goal change (r=0.004, p=0.427; n=38,531). The Lab uses a separate all-data model for retrospective exploration. Moving a budget slider changes a model input; it does not establish what a transfer would cause.

Hand over: “The application makes those distinctions visible and lets us inspect the evidence for individual clubs.”

The application and the demo

Scope: API → page states → comparison → scenarios → live demo

What you need to know

  • What an API is here: a small set of web addresses (endpoints) that return prepared results as JSON — plain text data that a browser can read. The browser asks, the server answers with a few hundred rows, never with the millions of raw rows in the database.
  • Why that matters: the SQL, the validation and the credentials stay on the server. The page only displays what the server already prepared and checked.
  • The numbers of your own demo pair, so you never read them off the screen for the first time while presenting: in Serie A 24/25 Inter recorded 79 GF, 35 GA and +44 GD (attack rank 1, defense rank 2) and Milan 61, 43 and +18 (ranks 3 and 7); their two meetings ended 1–2 and 1–1, so the head-to-head total is 2–3.
  • The three states that are easy to confuse: no coverage for this league and season, coverage exists but the two clubs never met, and a real completed 0–0 draw. The interface shows a different message for each and never invents a score.
  • What the HTTP status codes mean in our app: 422 means the input is invalid, for example the same club selected twice; 404 means the requested club or season is not in scope; 503 means the data or the model is not ready yet, which is a readiness problem, not a bad request.
  • How head-to-head goals are counted: for each completed meeting we take the selected club's perspective, so its goals are the home score when it played at home and the away score otherwise. Swapping the two clubs swaps the totals. Wins, draws and points follow from those scores.
  • What protects the Lab inputs: the server rejects values that are not finite numbers, checks the allowed range and refuses an attacking budget larger than the total budget. The sliders also limit the range, but the server check is the one that matters, because anyone can call the API directly.
  • Every new field reads from a table only after checking that the table exists. If the optional match data was never loaded, the API answers “absent” instead of failing — that is why the demo survives a partial setup.
  • What the automated checks cover: 43 unit tests, 16 live API checks and 15 real-browser checks, including mobile layout at 390 pixels. They are scoped evidence, not proof that no bug exists.

What to show

  1. Open /api/docs and call one endpoint live, then show the same numbers on the page: the page is a view of the API, not a separate truth.
  2. Open a comparison for two clubs in a season with match data, then switch to a league-season without it and read the coverage message aloud.
  3. In the Lab, move one input, show the new prediction, then press Reset and explain that a slider changes a model input, not reality.

Your spoken part

The browser reads a bounded API over prepared results. League and season filters are explicit, and the URL preserves the selected scope. In the comparison, season totals and actual head-to-head meetings are separate. Serie A 24/25 shows Inter at 79 for and 35 against (+44), ranked first in goals scored per match and second in goals conceded per match. Milan has 61 for and 43 against (+18), ranked third and seventh. The source has no xG field. For Inter and Milan in 24/25, the recorded league scores are 1–2 and 1–1, giving head-to-head goals of two to three. Missing match enrichment is reported explicitly. The Lab loads the five real club-season inputs, calls a saved model and rejects invalid budgets or non-finite numbers. We verify behavior at three levels: regression tests, live data contracts and desktop/mobile browser checks.

Infrastructure and measurements

Scope: Compose → readiness → reproducibility → time, memory, disk, growth

What you need to know

  • The startup order: database healthy, then the loader finishing successfully, then the pipeline finishing successfully, then the application. Waiting for a successful exit is different from merely starting a process, and that difference is what keeps the app off half-loaded data.
  • A named volume holds the database, while bind mounts carry the CSVs, the model and the measurement results. Credentials and raw data stay out of Git and out of the Docker build context.
  • The measurement method: three repetitions, the mean and the individual runs kept, one factor changed at a time, and the laptop's processor and memory recorded.
  • The 31.10-second full start applies to prepared CSVs and existing images. It is not the time of a first download and build.
  • The index comparison runs 300 identical selective lookups on the same sample; the 25/50/100% experiment is a separate aggregation over the largest table.
  • Memory is the largest working set observed in docker stats, sampled about every two seconds — not a continuously measured true peak.
  • What has to be ready before the defense: data and images prepared, a working laptop, saved results, the PDFs, and a two-minute backup recording.

What to show

  1. Open docker-compose.yml and follow the dependencies and mounts, without showing any credentials.
  2. Open README and MEASUREMENTS.md: the machine, the three runs, the conditions and the growth experiment.
  3. Explain the difference between the 31.10 s startup, the 10.8724 s and 0.0748 s query times, and the import time of a single CSV.

Your spoken part

Docker Compose coordinates four core services. The database must be healthy, loading and processing must finish successfully, and then the application starts. Source files, the model and measurement results use explicit mounts. We measured timing, observed memory, disk footprint and growth in separate experiments, each repeated three times. Complete cached-source startup averaged 31.10 seconds on an Apple M3 Pro with 18 GiB RAM. The selective index lookup improved by about 145 times, but that result applies to that query and sample. Caches were retained, image builds were excluded and brief memory peaks may have been missed.

Plain-language glossary

Short, non-technical definitions of every term the examiner may use.

Container / Docker ComposeA container is one packaged program with everything it needs to run. Compose is the file that starts our four containers in the right order: the database first, then the loader, then the processing pipeline, then the web application.
Relational database / PostgreSQLA store of tables with fixed columns that can be combined by shared keys. We use PostgreSQL 16. Combining two tables on a shared key is called a join.
SchemaThe declared shape of the tables: which columns exist and what type each one holds. It is written in sql/schema.sql.
COPY and indexCOPY loads a whole file into a table in one stream. An index is a lookup structure, like the index of a book: it makes selective queries fast and is built after the bulk load.
PipelineThe processing step between the database and the web page. It reads tables, computes our measures and the model, and writes prepared result tables back.
API / endpoint / JSONThe API is the set of web addresses the page calls. Each address is an endpoint. JSON is the plain-text format of the answer.
Champagne IndexOur own measure of attacking output: recorded goals plus assists, divided by the number of matches the source reports for that club-season. It is a proxy, not an official statistic.
Target and featureThe target is what the model tries to predict — here the change in the index in the next consecutive season. A feature is an input the model uses to predict it.
Chronological holdoutWe train the model on earlier seasons and test it on later seasons it has never seen. A random split would mix the future into the training data and flatter the result.
BaselineThe simplest possible prediction, used for comparison. Ours predicts no change at all. A model is only useful if it beats the baseline on the same test rows.
R² and MAER² is the share of variation the model explains, from 0 to 1 — ours is 0.127, which is weak. MAE is the average absolute error in index units — ours is 0.4856 against a baseline of 0.5114, about 5% better. Neither is a percentage of correct answers.
Correlation vs. causationA correlation (r) measures how two numbers move together, from −1 to +1. It cannot show that one causes the other. Every result in this project is a correlation, including the red-card and spending findings.
ProxyA measurable stand-in for something we cannot measure directly. Our shots-on-target estimate is a proxy for chance quality; it is not xG, which the data source does not contain.
Poisson ratingA simple statistical model of how many goals each team scores and concedes, fitted to one league-season. It describes that season; it does not forecast new matches.
SHAPA method that attributes a model's prediction to its individual inputs, so we can report which feature mattered most without relying on the model's internal importance score.

nedalozanovska

Why PostgreSQL rather than MongoDB?

The source tables have fixed columns and relational links by player, club, season and competition. PostgreSQL supports those joins, native COPY and indexed lookups with a clear schema. A different database could work, but this choice follows the data shape.

nedalozanovska

What identifies one observation?

For the analytical output it is club ID, season and competition ID. A club’s display name is a label, not its identity. We aggregate canonical keys to prevent alias names from creating duplicate observations.

nedalozanovska

Why build indices after loading?

Maintaining indices during a bulk load adds work to every inserted row. We import with COPY, then build the required indices and ANALYZE the updated tables so the next pipeline has current planner statistics.

nedalozanovska

Is your source openly licensed?

We verified the pinned source revision, headers and checksums, but did not establish an explicit upstream licence. We document this as unresolved and exclude raw data from the repository. Public downloadability alone is insufficient.

nedalozanovska

What happens if a download is interrupted?

The downloader writes a temporary file and installs it atomically only after checksum and header validation. An interrupted or corrupt download is not accepted as a complete source. Tests exercise these failures using fake HTTP responses.

nedalozanovska

How do you handle duplicate match rows?

Identical league/season/date/home/away fixtures are imported once. Conflicting scores for the same fixture stop replacement before stored match rows are changed. Missing optional input clears old enrichment on the next loader run.

lilllaz

Is Champagne Index an official metric or xG?

No. It is this project’s proxy: recorded goals plus assists divided by source matches. A goal with an assist contributes twice. We explain the denominator and do not present it as xG or an official rating.

lilllaz

What exactly does the model predict?

The next consecutive season’s Champagne Index minus the current index. It does not predict a match score, a calibrated league position or the causal return from buying a player.

lilllaz

Why reject gaps between seasons?

A club may leave a competition and return years later. shift(-1) gives the next recorded row, which is not necessarily next year. We explicitly require a one-year gap and adequate coverage in both seasons.

lilllaz

Why use a temporal split?

A random row split mixes earlier and later seasons and can make historical evaluation overly optimistic. We train on earlier seasons and test on later ones, keeping observations from the same season together.

lilllaz

How much better is the model than a baseline?

On the same 5,585 held-out rows, MAE is about 0.4856 versus 0.5114 for predicting no change. That is about a five percent reduction in MAE, a modest gain. R-squared is about 0.127, not a percentage of correct predictions.

lilllaz

Can you conclude that buying attackers improves performance?

No. These are retrospective observational data with confounding and source limitations. A slider changes a model input and shows a learned association, not the outcome of a controlled transfer intervention.

lilllaz

Why is the Lab model different from the evaluation model?

The evaluation model uses only earlier training data and is scored on held-out later seasons. A separate model is refitted on all eligible data for exploration. Its own training fit is not claimed as independent test performance.

lilllaz

Why did the index-position correlation change after the audit?

The earlier result mixed a partial 25/26 attacking snapshot with full final standings. We now require adequate comparable coverage. The corrected same-season association is about minus 0.793 over 388 observations.

jacoposcaccianoce

Why have an API instead of plotting raw tables directly?

The API exposes small prepared outputs under an explicit league and season. This avoids moving millions of raw rows to the browser, keeps SQL and validation on the server and separates presentation from processing.

jacoposcaccianoce

How are head-to-head goals calculated?

For each completed meeting, the selected club’s perspective determines whether the home or away score is goals for. Reversing the compared clubs swaps their totals. Wins, draws, losses and points are derived from those actual scores.

jacoposcaccianoce

Does no recorded match mean a 0–0 draw?

No. No coverage, no recorded meetings and a completed 0–0 draw are different states. The API reports enrichment availability and the interface shows an explicit message instead of inventing a score.

jacoposcaccianoce

What prevents invalid scenario inputs?

The API rejects non-finite numbers, checks bounds and requires attacking spend not to exceed total spend. The browser also clamps the sliders. Server-side validation remains necessary even when the UI enforces the same rule.

jacoposcaccianoce

What do HTTP 422, 404 and 503 mean here?

422 indicates invalid input, such as selecting the same club twice. 404 means the requested club-season scope is unavailable. 503 indicates temporary data/model unavailability or an incomplete application output state.

jacoposcaccianoce

What do your tests prove?

Regression tests cover known failure cases, live checks validate the prepared outputs and API contracts, and browser checks exercise actual flows and mobile layout. They provide scoped evidence, not a guarantee that every possible bug is absent.

Ataika

What starts when you run Docker Compose?

The database becomes healthy, then the loader must finish successfully, then the processing pipeline must finish, and finally the application starts. The measurement service is on demand and the legacy interface uses an optional profile.

Ataika

What does the 31.10-second measurement include?

A mean over three complete starts with prepared source files and existing images: containers are recreated, sources reimported and the model retrained until the API is ready. Network acquisition and image builds are excluded and caches are not flushed.

Ataika

Does the index make the whole application 145 times faster?

No. The measured gain is for 300 identical selective club lookups on the raw performance table, comparing index conditions. The frontend reads prepared outputs and a full GROUP BY has a different access pattern.

Ataika

Is your memory number a guaranteed peak?

It is the largest observed Docker working-set sample during three runs, sampled at roughly two-second intervals. Brief peaks may be missed. We report the method rather than label it a continuous or hardware-independent maximum.

Ataika

Why did four times as many rows not give exactly four times the query time?

Fixed costs, query plans, indexing, caches and hardware influence scaling. In this experiment four times the largest-table rows gave about 4.40 times the loading time and 3.35 times the aggregation time. That does not define a general law.

Ataika

Everyone

What is the main result in one sentence?

The system is reproducible on the measured setup, while historical transfer spending alone has almost no linear relationship with next-season index change and the richer model adds only modest predictive value.

Everyone

What is the most important limitation?

The data are retrospective and unevenly covered, the index is a proxy, and associations are not causal effects. Source licence and independent team/laptop validation also remain explicit unresolved requirements.

Everyone

How do goals for, goals against and goal difference work in the comparison?

GF and GA are season totals rebuilt from completed home/away match scores. GD is GF − GA. They come from the optional football-data.co.uk match enrichment, not from the Champagne Index player totals.

Everyone

How are attacking and defensive ranks calculated?

Within one league and season, attack rank orders goals scored per match from highest to lowest; defense rank orders goals conceded per match from lowest to highest. SQL RANK gives tied rates the same rank and leaves a gap after ties. They describe scores, not tactics or chance quality.

Everyone

Do we have xG or can we estimate it?

The source has no provider xG field. The comparison instead shows observed shots and shots on target. A separate estimate multiplies shots on target by the league-season average goals-per-shot-on-target rate; it is an experimental volume proxy with no shot-location or chance-quality input, not xG.

Everyone

What is the difference between the Champagne Index and attack rank?

The Champagne Index is recorded player goals plus assists divided by a Transfermarkt matches proxy for a club-season. Attack rank uses actual completed league scorelines, sums team goals and ranks goals per match within the league-season. Their sources, coverage and units differ.

Everyone

How did you check the goalkeeper defensive totals?

We compared Transfermarkt goalkeeper goals-conceded totals with the independent match-result totals on 388 adequately covered top-five club-seasons. They match exactly in 366 (94.3%). Clean sheets match only 269 (69.3%), so the scoreline source remains the basis of league ranks.

Everyone

What does the defensive-spend analysis show?

The Pearson correlation between defender transfer fees and next-season change in the goalkeeper-source conceded-goal rate is r=0.004047, p=0.426997, n=38,531. The sample does not support a useful linear association. It is descriptive, not causal. A separate match-level check finds teams with a red card concede 0.341 more goals on average in the same match, but match context confounds that association.

Everyone

Why keep the player-source defensive values separate from scoreboard goals?

The sources use different records and denominators. Goalkeeper conceded totals agree with scorelines in 94.3% of adequately covered seasons, while clean sheets agree in 69.3%. The UI therefore uses match scores for GF, GA, GD and ranks; player-source totals remain a quality cross-check. Shots and corners are also observed match statistics, not chance-quality measures.

Everyone

Is the shot-based estimate the same as xG?

No. It multiplies a team’s shots on target by the league-season average goals per shot on target. It has no shot-location, distance, body-part, pressure or goalkeeper-position input. It is a rough volume benchmark and must be called an SOT-based proxy, not provider xG.

Everyone

What does the Poisson attack/defense rank tell us?

The model fits attack, defense and a shared home-advantage term to the selected league-season scores. Larger fitted attack and defense parameters mean stronger estimated attack and defense. Its ranks are descriptive and in-sample; the separate chronological RandomForest evaluation is the project’s held-out prediction check.

Everyone

Did the added defensive features improve the model?

On the same chronological split, R² moves from 0.1271 with the five-feature baseline to 0.1502 after adding goalkeeper conceded rate, discipline and net spend; MAE moves from 0.4856 to 0.4788 on 5,585 held-out rows. The gain is modest, and it does not isolate a causal effect of defense.

Everyone

Do red cards cause more goals to be conceded?

The local sample shows a same-match difference of +0.341 conceded goals per team-match (1,619 sent-off vs 16,195 others; Welch p < 0.0001). This is observational: stronger opponents, match state and timing can affect both red cards and goals. It is not a causal estimate.

How to answer questions

  • Answer in three steps: one short sentence, then the evidence (a file or a number), then the limitation.
  • Give every number with its sample and unit: “r = −0.79 across 388 club-seasons, within the same season”, not “the correlation is high”.
  • If you do not know, say where the answer lives instead of guessing: “that is in docs/MEASUREMENTS.md, the memory sampling method is described there”.
  • If the question belongs to someone else's part, hand it over in one sentence rather than approximating their area.
  • Never turn an association into a cause. Say “accompanies” or “is associated with”, never “causes” or “improves”.
  • If asked about a weak point, answer it first and directly. An acknowledged limitation is stronger than a defended inaccuracy.
